Jev, explained: typed decisions instead of generated text

What TypeSafe’s Jev is, how its three question types work, why it is fast, and why its confidence number is not the same thing as being right.

An agent spends most of its time on small decisions, not on writing. Is this retrieved passage relevant? Which model should handle this request? Is this shell command safe to run? Each one sits on the critical path, and each one usually becomes an LLM call that returns a few tokens of JSON.

Jev, from TypeSafe, is built for exactly those decisions. It can’t write a sentence. You give it some text and a set of typed questions, and it returns probabilities your code can act on.

This post covers what Jev is, how its three question types work, why it’s fast, and the part that is easiest to get wrong: what its confidence number does and doesn’t tell you. Every Jev number below comes from requests I ran myself with the script in this post’s code/ folder. TypeSafe’s own claims are labelled as such.

What Jev is

TypeSafe calls Jev a System One model, after the fast, intuitive “System 1” thinking that Daniel Kahneman popularised in Thinking, Fast and Slow. 1 The contract is simple:

  • In: a state (a message, a document, a JSON record) and one or more named questions.
  • Out: for each question, a probability distribution over the answers you defined. You don’t get text.

That last point is the whole design. An LLM asked for JSON still writes that JSON one token at a time, and a field like "confidence": 0.95 is just more tokens chosen to fit the prompt. Jev’s answer space is fixed by your request, so it can only choose among your options, and the probabilities are its actual output.

Jev can't generate text

No replies, no summaries, no explanations of its answers. 1 If a step needs words, it still needs an LLM. Jev replaces the decision calls, not the writing calls.

The three question types

Every question is one of three primitives. 2

PrimitiveUse it forYou defineYou get back
noulYes/no questionsInstructionsThe probability that the answer is yes
choicePicking one of a setInstructions, plus named options (up to 255) 3The top option, the probability of every option, and confidence
scoreA position on ordered scaleInstructions, plus a description of each levelA score (can fall between levels), plus confidence

One request, five questions

TypeSafe’s docs use a support ticket that mixes three problems: a double charge, a login failure, and a feature request. 4 Here it is with TypeSafe’s Python SDK. The full script, which also times the requests, is code/measure.py (see how these numbers were measured).

What jev-1.13.0 returned, from one request of 544 input tokens:

Two things stand out. The ticket is about a double charge, a login failure and a feature request, but a choice has to pick one: billing got 0.85, account only 0.06 and feature_request 0.00. If a ticket can carry several issues, ask one noul per issue instead. And bug_severity came back as 1.85, close to “blocking”, on a ticket that isn’t a bug report. That’s a speculative answer, and your code should ignore it, as the fan-out section shows.

Reading a score

A score is not “the most likely level”. TypeSafe defines it as a probability-weighted mean of the level numbers. 5

score=∑ii⋅P(level i)\text{score} = \sum_{i} i \cdot P(\text{level } i)score=i∑​i⋅P(level i)

For bug_severity, Jev put 0.15 on level 1 and 0.85 on level 2, which gives 1×0.15+2×0.85=1.851 \times 0.15 + 2 \times 0.85 = 1.851×0.15+2×0.85=1.85. A score between two levels means the probability is split between them. It is not a percentage of anything.

Confidence is not correctness

confidence on a choice or score answer is, in TypeSafe’s words, “a statistic computed from the probability distribution the answer already gives you”. 6 Probability concentrated on one option gives high confidence, and spread-out probability gives low confidence.

Two consequences:

  1. The exact formula isn’t public. Open-source look-alikes such as Nimble describe their confidence as “entropy concentration”. 7 For Jev’s category answer, one minus the normalised entropy gives 0.62, while Jev returned 0.79. For bug_severity it’s 0.62 against 0.77. Jev’s number is consistently higher, so TypeSafe uses a different formula. TypeSafe itself says you’re not locked into its measure: every answer includes the full probabilities, so you can compute your own. 6
  2. High confidence doesn’t mean a correct answer. Confidence is calculated from the answer itself, so it can’t tell you whether the answer is right. TypeSafe says the same about calibration: it “is measured across groups of predictions; it does not guarantee that an individual answer is correct”. 1

So the question to ask is whether the probabilities are calibrated: among many answers given probability 0.8, are about 80% actually right? That needs labelled examples. One standard measure is the Brier score, the mean squared gap between probability and outcome:

Brier=1N∑n=1N(pn−yn)2,yn∈{0,1}\text{Brier} = \frac{1}{N}\sum_{n=1}^{N} (p_n - y_n)^2, \qquad y_n \in \{0, 1\}Brier=N1​n=1∑N​(pn​−yn​)2,yn​∈{0,1}

Confident mistakes cost the most: a wrong answer given 0.9 adds 0.81, while one given 0.6 adds 0.36. Measuring this for Jev on a labelled task is part 3 of this series.

Rule of thumb

Use Jev’s probability to rank and threshold. Before you let it act automatically, check it against a few hundred labelled examples from your own task.

Why it’s fast

An LLM returning structured output generates it sequentially: each token waits for the one before it. Jev evaluates every question in parallel and in isolation against the same state, and TypeSafe says adding questions “barely changes the response time”. 2

I checked that claim. Same ticket, 20 timed requests for each question count (after one warm-up), sent from my machine:

Questions per requestMedianp90
1407 ms428 ms
5410 ms448 ms
20411 ms611 ms

Going from 1 question to 20 moved the median by 4 ms. Only the slowest runs grew: the p90 rose from 428 to 611 ms. These timings include the network round trip, so treat them as what an application sees rather than model speed.

TypeSafe’s own cookbook reports that batching 13 questions into one call was 12.2× cheaper and 10.0× faster than asking them one per call, with no change in answers. That’s a vendor measurement. 8 Pricing is $0.042 per million input tokens, and output tokens are free. 9

How can a model do this?

TypeSafe hasn’t published Jev’s architecture. It trains Jev with what it calls reinforcement learning for calibrated decisions (RLCD), aimed at returning decisions and calibrated probabilities instead of text. 10

Open-source look-alikes show that the interface itself is buildable. Nimble, for example, trains an ordinary language model with cross-entropy over a small set of single-token answer codes at the last prompt position. It then reads the probabilities of just those codes, so there’s no decoding loop. 7 What a look-alike doesn’t copy is the training objective. A generic model’s probabilities are not calibrated just because they come out of a softmax. That’s the gap Jev claims to close, and the one you have to measure.

Speculative fan-out: ask everything, then branch in code

Because extra questions are nearly free, TypeSafe recommends a pattern it calls speculative fan-out. 4 Don’t ask “what category?” and then make a second call for “how severe?”. Ask every question you might need in one request, and let your code decide which answers matter.

  1. Decompose. Turn the decision into narrow typed questions, not one big “what should I do?”.
  2. Fan out. Send all of them in one request against the same state.
  3. Branch in code. Read only the answers the branch needs. Thresholds decide when to act and when to escalate.

For our ticket, category.confidence is 0.79 and the choice is billing, with refund_requested at 0.16, so this code routes it to billing. The 1.85 severity score is never read.

The model handles the fuzzy judgment, and your code keeps control of the workflow. The routing logic is ordinary code that you can test, log and change without re-prompting.

Limits to know before you reach for it

  • No text output. It decides; it doesn’t explain. 1
  • Small context. A request allows 64K tokens in total, with 32K for the state plus the longest question. 9 Keep state compact and questions atomic.
  • Documented weak spots. TypeSafe’s own “jaggedness” page lists where jev-1.13 struggles. That includes reading instructions too literally, counting, arithmetic, comparing dates, and large states full of irrelevant detail. 11 Do the counting and maths in code.
  • Instructions are the only tuning knob. The same weights serve every account; you shape answers through the state and the wording of each question. 9

Where I’d use it

  • Routing. Pick the model and reasoning effort for a request, or send it to the right agent.
  • Guardrails. Score every proposed tool call or shell command before it runs.
  • Filtering and reranking. Score retrieved passages for relevance at a price you can pay on every step.
  • Triage. Tickets, alerts and documents, using the fan-out pattern above.

In each case the job is a bounded decision on a hot path, where the probability is useful to code and nobody needs prose.

How these numbers were measured

All Jev numbers in this post come from one run of code/measure.py on 26 September 2026 (UTC), against the pinned model jev-1.13.0. The run sends the triage request once, then 20 timed requests (after one warm-up) for each question count. It costs well under one cent. To reproduce it, run pip install typesafe-sdk, set TYPESAFE_API_KEY, then python3 measure.py. Raw results are saved to results.json.
