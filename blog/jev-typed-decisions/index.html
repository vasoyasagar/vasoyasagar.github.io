Jev, explained: typed decisions instead of generated text

What TypeSafe’s Jev is, how its three question types work, why it is fast, and why its confidence number is not the same thing as being right.

An agent spends most of its time on small decisions, not on writing. Is this retrieved passage relevant? Which model should handle this request? Is this shell command safe to run? Each one sits on the critical path, and each one usually becomes an LLM call that returns a few tokens of JSON.

Jev, which TypeSafe released in early access on September 15, 2026, is built for exactly those decisions. 1 It can’t write a sentence. You give it some text and a set of typed questions, and it returns probabilities your code can act on.

This post covers what Jev is, how its three question types work, why it’s fast, and the part that is easiest to get wrong: what its confidence number does and doesn’t tell you. I haven’t benchmarked Jev myself yet (that’s part 3 of this series). Every number below is quoted from its source, and TypeSafe’s own claims are labelled as such.

What Jev is

TypeSafe calls Jev a System One model, borrowing Daniel Kahneman’s term for fast, automatic judgment. 2 The contract is simple:

  • In: a state (a message, a document, a JSON record) and one or more named questions.
  • Out: for each question, a probability distribution over the answers you defined. You don’t get text.

That last point is the whole design. An LLM asked for JSON still writes that JSON one token at a time, and a field like "confidence": 0.95 is just more tokens chosen to fit the prompt. Jev’s answer space is fixed by your request, so it can only choose among your options, and the probabilities are its actual output.

Jev can't generate text

No replies, no summaries, no explanations of its answers. If a step needs words, it still needs an LLM. Jev replaces the decision calls, not the writing calls.

The three question types

Every question is one of three primitives.

In that post, jev-1.13.0 classified the ticket as bug_report with probability 1.0, put the chance of reproducible steps at 0.88, and returned frustration with a score of 0.86 and a confidence of 0.78.

Reading a score

A score is not “the most likely level”. It is the expected level: every level weighted by its probability.

score=∑ii⋅P(level i)\text{score} = \sum_{i} i \cdot P(\text{level } i)score=i∑​i⋅P(level i)

For frustration, Jev put 0.14 on level 0 (“Calm and factual”) and 0.86 on level 1 (“Frustrated but civil”). That gives 0×0.14+1×0.86=0.860 \times 0.14 + 1 \times 0.86 = 0.860×0.14+1×0.86=0.86. So a score of 0.86 means “mostly level 1, with some pull towards level 0”. It does not mean 86% of anything.

Confidence is not correctness

confidence on a choice or score answer measures how concentrated the distribution is. When all the probability is on one option, it’s 1. When the probability is spread evenly, it’s close to 0. TypeSafe describes it as a statistic derived from the distribution. 5

Two consequences:

  1. The exact formula isn’t public. Nimble, an open-source Jev look-alike, measures “entropy concentration”: one minus the normalised entropy. 6 7 On the frustration answer that formula gives 0.63, while Jev returned 0.78. So treat open-source formulas as approximations, not as Jev’s definition. TypeSafe itself says you’re not locked into its measure: every answer includes the full probabilities, so you can compute your own. 5
  2. High confidence doesn’t mean a correct answer. Confidence is calculated from the answer itself, so it can’t tell you whether the answer is right. Only labelled outcomes can.

Praneeth Paikray measured the second point on a medical-literature task. On 300 test sentences, Jev returned confidence = 1.0 150 times, and 10 of those answers disagreed with the dataset’s labels. 1 The question to ask is whether the probabilities are calibrated. Among many answers given probability 0.8, are about 80% actually right? One standard way to measure that is the Brier score, the mean squared gap between probability and outcome:

Brier=1N∑n=1N(pn−yn)2,yn∈{0,1}\text{Brier} = \frac{1}{N}\sum_{n=1}^{N} (p_n - y_n)^2, \qquad y_n \in \{0, 1\}Brier=N1​n=1∑N​(pn​−yn​)2,yn​∈{0,1}

Confident mistakes cost the most: a wrong answer given 0.9 adds 0.81, while one given 0.6 adds 0.36.

The result can still favour Jev. In a routing benchmark of 330 requests, Paikray counted mistakes made with at least 90% confidence: GPT-6 Luna made 31 and Jev made 7. 2 That comparison is the point. Jev’s probabilities are useful precisely because you can check them against outcomes and set thresholds on them.

Rule of thumb

Use Jev’s probability to rank and threshold. Before you let it act automatically, check it against a few hundred labelled examples from your own task.

Why it’s fast

An LLM returning structured output generates it sequentially: each token waits for the one before it. Jev evaluates every question in a request in parallel against the same state, and each answer comes from one scoring step over a small, fixed answer set.

Aman Arora sent the same state and three questions to both. Jev answered in 299 ms, and GPT-5.6 Luna (with reasoning off) in 1,114 ms, about 3.7× slower. 4 That’s a single request, not a benchmark, but the direction matches the design.

TypeSafe’s launch claims are much larger: 193.6× faster and 444.6× cheaper on its selected workflow evaluations. 1 Those evaluations were built by TypeSafe, so treat them as the vendor’s upper bound. In September 2026, pricing was $0.042 per million input tokens, and output was free. 2

How can a model do this?

TypeSafe hasn’t published Jev’s architecture. It describes the training objective as Reinforcement Learning for Calibrated Decisions (RLCD), aimed at making the probabilities trustworthy. 1 Open-source look-alikes show that the interface itself is buildable:

  • Nimble gives each allowed answer a one-letter code (A, B, …). It then runs an ordinary language model once and reads the probabilities of just those letters, with no decoding loop. 6 Aman Arora rebuilt this on Qwen3-0.6B. 7
  • DiffusionGemma, via a vLLM pull request by Matt Mastracci, pins the whole prompt on a diffusion model’s canvas, leaves one slot open, and reads the option probabilities from a single denoising step. 2

What these don’t copy is the training. A generic model’s letter probabilities are not calibrated just because you put them in a softmax. That’s the gap Jev claims to close, and the one you have to measure.

Speculative fan-out: ask everything, then branch in code

Because extra questions are nearly free, TypeSafe recommends a pattern it calls speculative fan-out. 8 Don’t ask “what category?” and then make a second call for “how severe?”. Ask every question you might need in one request, and let your code decide which answers matter.

  1. Decompose. Turn the decision into narrow typed questions, not one big “what should I do?”.
  2. Fan out. Send all of them in one request against the same state.
  3. Branch in code. Read only the answers the branch needs. Thresholds decide when to act and when to escalate.

The model handles the fuzzy judgment, and your code keeps control of the workflow. The routing logic is ordinary code that you can test, log and change without re-prompting.

Limits to know before you reach for it

  • No text output. It decides; it doesn’t explain.
  • Small context. A request allows 64K tokens in total, with 32K for the state plus the longest question. 9 Keep state compact and questions atomic.
  • Documented weak spots. Jev doesn’t count reliably, compare dates or do arithmetic, and TypeSafe’s own “jaggedness” page lists nine failure modes, including reading instructions too literally and trouble with multi-hop questions. 2 Do those steps in code.
  • Instructions are the only tuning knob. Jev is one hosted model, so you adapt it through how you word the questions. Paikray used GEPA to rewrite the question automatically and raised F1 from 69.1% to 79.7% on a fresh test set. 1

Where I’d use it

  • Routing. Pick the model and reasoning effort for a request, or send it to the right agent.
  • Guardrails. Score every proposed tool call or shell command before it runs.
  • Filtering and reranking. Score retrieved passages for relevance at a price you can pay on every step.
  • Triage. Tickets, alerts and documents, using the fan-out pattern above.

In each case the job is a bounded decision on a hot path, where the probability is useful to code and nobody needs prose.
